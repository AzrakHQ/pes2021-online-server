Technical write-up: how PES 2021 talks to its servers

The full reverse-engineered network protocol of eFootball PES 2021 (1.01.00, Steam), as implemented by this project's server. Last update: 2026-11-05.

In plain words: the game connects to a "gate" server on TCP port 10000 and exchanges small messages written in MessagePack, each compressed, encrypted with Blowfish and sealed with a checksum. A few extra requests go over HTTP and HTTPS, and a STUN check measures your network. Matches themselves run directly between the two players. The main page tells the story; this page has the details for developers: byte layouts, keys, every command and the code addresses they were found at.

Layer stack (gate connection)↑ Contents

Gate exchange↑ Contents

Correction (2026-11-04). The 152-byte "hello" is not a key exchange. It is an ordinary CMD_GET_SVRLIST request, and the client speaks first. The RC4 / dlcp code found earlier is real, but it is a different link (see Not the gate). The old "reply must be 16 bytes" result was a side effect: our reply was decoded as a command, and a 16-byte body produced a garbage length that crashed the client's MessagePack reader.

Login sequence (live)↑ Contents

  1. GATE (tcp/10000): CMD_GET_SVRLIST → CMD_GET_URLLIST → CMD_GET_SVRVERSION → CMD_GET_SVRTIME → CMD_GET_EULA_NATION_LIST → CMD_GET_EULA_NATION_CODE → CMD_DISCONNECT logoutstat=MOV. A second gate session fetches CMD_GET_GLOBALINFOTITLELIST. LIVE
  2. First run only: Country/Region picker (from our nation list) and Terms of Use screen (documents opened via ShellExecute on URL-list entries EULA_*). Persisted locally once a full login succeeds. LIVE
  3. HTTP POST to the URL-list entry AUTH_STEAM: form msgid=CMD_AUTH_STEAM&rqid=0&urltype=AUTH_STEAM&steamid=…&package_type=DEFAULT; reply is a raw msgpack map (JSON is rejected with C_GKCC_0008_200). LIVE
  4. ACCOUNT (same socket, svrtype ACCOUNT): CMD_SEND_HEARTBEAT, CMD_GET_CHALLENGECODE, CMD_LOGIN {username, hash, platform PC, sku}, CMD_SEND_PSID, CMD_GET_PLAYER_DATA (has_data NO → "Create User Data" screen → CMD_CREATE_PLAYER {name}), CMD_SET_LANGUAGE, CMD_DISCONNECT MOV. LIVE
  5. MENU (new connection): CMD_LOGIN, CMD_SET_CURRENTPLAYER → reply carries key (base64) + key_size; the client switches its Blowfish key to base64-decode(key) for every later frame. Then CMD_GET_STORE_PRODUCT_LIST, CMD_GET_GP_ACHIEVEMENT, CMD_GET_STORE_TRANSACTION_STATE, heartbeats every 30 s. LIVE
  6. Live update: LiveDataSetFlow (0x1420ac3f0) POSTs CMD_GET_DLC_FILELIST (file_type LIVEDATA, region REGION_ALL) to the URL-list type FLOW. Without a FLOW URL it fails locally ("New data asset download unsuccessful", then logout FIN). Answering with empty lists and dlc_version "1.00" gives "No new Live Update available" and the client proceeds. LIVE
  7. Online main menu: CMD_GET_GLOBALINFOTITLELIST, CMD_GET_PRIVATEINFOTITLELIST, CMD_GET_DMM_PLAYERINFO, CMD_SEND_LOG. LIVE
  8. The client caches the URL list for the whole game session; URL-list changes need a fresh title login. LIVE

NAT test ("Testing network environment")↑ Contents

  • Resolves ntl.service.konami.net, sends 32-byte UDP probes to port 3478, opens TLS to port 443, and does UPnP discovery against the LAN router. LIVE
  • Its UDP socket is bound to the network interface, so it cannot reach 127.0.0.1 — the redirect target must be the machine's LAN address. LIVE
  • Probe order: (1) 32-byte Binding Request with vendor attr 0xF000 (8 bytes: 05730000 00000002); (2) TLS to port 443 with SNI ntl.service.konami.net (no HTTP request seen after the handshake yet); (3) 64-byte Binding Requests every 5 s with vendor attrs 0x9090 (24 B, starts 10000001) and 0x9091 (12 B, 00010104 00000000 <counter>). The keepalives need more than a plain Binding Success (see next item). LIVE
  • A plain Binding Success (XOR-MAPPED + MAPPED, same tid) is accepted for the 0xF000 "MappingTestIA" probe. The 0x9090/0x9091 packets are post-test keepalives (RP_P2P_HEADER / RP_RELIABILITY); a new serial every 5 s means they are being answered. Don't send OTHER-ADDRESS unless a real alternate IP:port exists. LIVE
  • GateInfo.php: POST https://ntl.service.konami.net/ntl/api/GateInfo.php, User-Agent NTL HttpModule/0.1, body req={"titleCode":"PES2021",…}. WinHTTP default certificate validation (no pinning) — solved by a private CA, name-constrained to konami.net, that the join line trusts: on Windows in the machine Root store, on Linux only inside the game's Proton prefix (server/pesserver/web/install-ca-proton.py writes it into system.reg). Reply is text lines: STATUS: 200, API_STATUS: 0, LOG_ACTIVE: 0, SERVER_TIME: <unix>. LIVE

Matchmaking — live↑ Contents

  1. eFootball → NAT test → live-update check → CMD_SEND_IPANDPORT_NTL (host_addr blob with raw sockaddr) → CMD_GET_GAME_TEAM_LIST, CMD_GET_SERVER_ENV, CMD_CHECK_CHEAT, CMD_GET_URGENT_ANNOUNCEMENT (online_mode QUICK), CMD_GET_MANNER_WARN. LIVE
  2. Select Team → CMD_GET_QUICKMATCHOPTION → "Matchmaking Settings" → Go to Matchmaking → CMD_GET_MAINTENANCE_INFO, CMD_START_MATCHING {matching_type OC_QUICK, has_guestplayer, guest_info}. LIVE
  3. Both clients show "Matchmaking — Searching for an opponent" and never poll; the server paired them ("MATCH FOUND room 1"). LIVE
  4. Server push CMD_WATCH_MATCHING (kind 0x60, seq 1, rqid 0): pushes are routed by msgid only to watches the client registered (0x141239840 / 0x1412395f0). The key field is matching_state: FINISH → match accepted; missing → ignored → 300 s timeout = error EYRH763 (line 763 of the quick-match task). Members: blobs {pid, pname, is_owner YES/NO, matching_order, host/reflexive/relayed_addr, ntl_nat_type}. LIVE
  5. Game relay: CMD_GET_GAMERELAY is an HTTP web-API call to URL-list type GET_GAMERELAY (then GET_TURN_SERVER_LIST as fallback). Missing type → instant local failure ER_MATCHING_RETRY. We now serve all 53 URL types from the client's enum (0x14021ee70), short paths to fit one frame. LIVE
  6. Peer signalling: clients send CMD_SEND_SYNC_NOTICE / SEND_SYSTEM_NOTICE {pid_list, data} ("1,", "END:pid=2;time=…"); the server must relay each as CMD_WATCH_SYNC_NOTICE / WATCH_SYSTEM_NOTICE {data} to the listed pids. With relay on, both report CMD_SET_GAMERELAY_CHECK_RES {game_sycom P2P, error_code NOERR} and exchange UDP directly; server pushes CMD_WATCH_GAMERELAY_CHECK_RES {error_code NOERR}. LIVE
  7. Then CMD_SEND_MATCHING_RESULT {member, vs_member, game_sycom P2P}, CMD_SET_GAMEMEMBER, CMD_SET_GAMEMEMBERENV {envlist pid/side/sideLeader}, CMD_GET_MATCHID, CMD_CHANGE_GAMEPHASE TEAMSELECT → MATCHMENU (online pre-match menu, shared countdown) → both players Kick Off → both GAMELOAD. LIVE
  8. Sides: every WATCH_MATCHING member blob needs side = HOME (owner) / AWAY. Without it the HOME team is never filled and team-data sync aborts with MMGC_0002 (MultiplayCmdTeamDataSync.cpp line 2). LIVE
  9. Team list: CMD_GET_GAME_TEAM_LIST must return the selectable clubs as blobs {team_id, team_class, division_point}; ids are the game's internal DB ids (100 Man Utd, 101 Arsenal, 108 Barcelona, 114 PSG, 116 Ajax, 120 Juventus, 127 Bayern, 131 Celtic). Empty list → no team to pick. LIVE
  10. Server environment: CMD_GET_SERVER_ENV timeouts must be real values (load_timeout 180, long_outofplay 120, init_not_end 240, cmd_lack 180 …). Zero-filled defaults made the client abort instantly with LOAD_TIMEOUT (QVHE1459, GameModeMatchListenerMatch.cpp) and then crash while tearing down match::Online. Lesson: an unhandled command gets a bare {result: NOERR} so the client keeps its own defaults — never zero-filled fields. LIVE

Match — live↑ Contents

  1. After MATCHMENU both clients Kick Off → CMD_CHANGE_GAMEPHASE GAMELOAD → ENTRY → 1ST. Gameplay itself is peer-to-peer UDP between the clients; the server only sees phase reports and events. LIVE
  2. Phases reported (each with gtimer, the game clock): DATASYNC, TEAMSELECT, MATCHMENU, GAMELOAD, ENTRY, 1ST, 1ST_15MIN, 1ST_30MIN, BREAK1 (half-time), 2ND, 2ND_15MIN, 2ND_30MIN, then the end of the match. A bare NOERR reply to each is enough. LIVE
  3. Events during play: CMD_ADD_FOUL (fouls, yellow cards); both clients report the same events, and their clocks stay in sync. LIVE CMD_ADD_GOAL exists in the client but no goal has been scored in a test match yet. STATIC
  4. Full time: both clients send CMD_CHANGE_GAMEPHASE {phase END, gtimer 94107} (90 min + stoppage), then show the highlights reel and match records. Post-match reporting: CMD_SET_PLAYDATA_MATCH (HTTP, URL type PLAYDATA_MATCH, JSON play_data), CMD_SEND_STATS_DATA {match_id, stats[] per side}, CMD_SEND_GAME_RESULT {game_phase END, side, home/away_score, home/away_team_id, abnormalend_reason NOERR, …}, CMD_REQ_GAMEADDPOINT, CMD_LEAVE_ROOM. A bare NOERR to each returns both players to the menu; a new Go to Matchmaking pairs them again straight away. Verified with a complete 90-minute match on 2026-11-04 (18:20–18:52, Arsenal v Arsenal 0–0). LIVE
  5. The player who leaves the post-match screens second reports DISCONN_P2P / GNCX_0003 (OnlineModeMultiplay.cpp): the peer link has already closed. The result is still recorded normally. LIVE
  6. Abnormal end: CMD_SEND_ABNORMALEND {reason, error_code}. Seen reasons: NO_OPERATION (a player gave no input for ~50 s; this is the game's AFK rule), DISCONN_P2P (peer link lost), LOAD_TIMEOUT. With real server-environment timeouts, both games returned to the menu without crashing (the LOAD_TIMEOUT crash in the matchmaking section happened only with zero timeouts). LIVE

Error codes↑ Contents

On-screen codes such as EYRH763 or MMGC_0002_0_… encode the source file and line: the four letters are a hash of the .cpp basename (characters bucketed by index mod 4, each bucket summed mod 26 + 'A'), followed by the line number. notes/re/errcode.py matches the letters against every source-file name in the binary's strings.

Deployment↑ Contents

  1. Host (Linux): curl -fsSL …/install.sh | sh installs Docker if needed and runs the server image (published as ghcr.io/mohamedalirashad/pes2021-private-server; built from the repo when it can't be pulled) with host networking. No configuration: netsetup.py finds the LAN IP, asks the router for its external IP and opens TCP 80/443/8080/10000 + UDP 3478/7600 over UPnP IGD (renewed every 30 min, removed on stop), checks the public IP against a what-is-my-IP service to detect CGNAT, and prints the player commands. Docker Desktop hosts use docker-compose.bridge.yml with a fixed PUBLIC_IP. LIVE
  2. Per-client address: SVRLIST / URLLIST / GAMERELAY carry the server address. Without a pinned PUBLIC_IP, a client from a non-global address (LAN, Tailscale 100.64/10, loopback) gets the local address its TCP connection reached (sockname); an internet client gets the public IP. One server serves LAN and internet players at once. LIVE
  3. Player setup is served by the server: irm http://SERVER/join | iex (PowerShell User-Agent → join.ps1, self-elevates) or curl -fsSL http://SERVER/join | bash (→ join.sh); a browser gets an instructions page. The scripts come with the address from the request's Host header filled in. On Linux the CA goes straight into the prefix's system.reg ([Software\\Microsoft\\SystemCertificates\\Root\\Certificates\\<SHA1>], "Blob"=hex: 20,00,00,00 01,00,00,00 len DER), so no Wine/Proton is needed; earlier server CAs are removed. Verified: GateInfo over HTTPS passes with a CA written this way. LIVE
  4. First start generates a private CA (name-constrained to konami.net) plus a certificate for ntl.service.konami.net, *.service.konami.net, *.cs.konami.net and *.konami.net (no IP addresses), in server-data/certs/; the CA is downloadable at http://<ip>:8080/ca.crt.
  5. Docker bridge vs. the NAT test: the client's STUN socket is bound to the network interface (Wine maps IP_UNICAST_IF to SO_BINDTODEVICE). A game on the same Linux PC as a bridged container therefore never reaches it: the DNAT'd packet must go out via docker0, but the socket is pinned to the NIC. Verified with a device-bound test socket (no reply on the bridge, reply with host networking). Remote players are unaffected. LIVE
  6. What the join scripts do: hosts-file entries for pes21-x64-gate.cs.konami.net, pes21-x64-stun.cs.konami.net, ntl / ntleu / ntlus / ntljp.service.konami.net, and trust the server CA (Windows: Import-Certificate into Cert:\LocalMachine\Root; Linux: the game's Proton prefix only). The CA carries a critical nameConstraints extension (permitted DNS:konami.net, all IPs excluded), so it cannot vouch for any other site. No change to the game files.

How it was tested↑ Contents

Every finding marked LIVE was checked against the game's original 1.01.00 executable, run directly under Proton on Linux (a run started through the Steam client is still pending). A recorded log of real client requests is replayed through the server's handlers offline and each reply is validated against the reply formats extracted from the game (server/test_ncl.py; the published repo replays the captured first frames in notes/re/captures, the full recorded log stays local). End-to-end runs drove two copies of the game on one Linux PC through login, the network test, matchmaking and complete 90-minute matches. The local test harness itself is not part of the published repo.

How we found it↑ Contents

  1. Wine's own debug channels (WINEDEBUG=+seh,+winsock) showed the client crashing in memcpy called from 0x1418568bb right after reading our reply.
  2. That function is the NclMio decoder: it builds a message object, decrypts the body, and switches on kind.
  3. The crypto factory 0x141856610 allocates a 0x1050-byte object for the easy tier — the size of a Blowfish context.
  4. 0x14116eeb0 installs a 56-byte key from .data when none is set.
  5. Blowfish-ECB with that key turned the captured "hello" into readable MessagePack.

Open questions↑ Contents

  • Game relay (TURN-style fallback for players who cannot reach each other directly): the server returns relay info, but UDP 7600 is only a logging placeholder. OPEN

Ratings, divisions and rankings are not implemented, and live goal events (CMD_ADD_GOAL) have not been seen yet because every test match ended 0–0. OPEN
