Technical write-up: how PES 2021 talks to its servers

The network protocol of eFootball PES 2021 (1.01.00, Steam), reverse-engineered as far as login, the network test and Quick Match need it, as implemented by this project's server. Last update: 2026-11-05.

In plain words: the game connects to a "gate" server on TCP port 10000 and exchanges small messages written in MessagePack, each compressed, encrypted with Blowfish and sealed with a checksum. A few extra requests go over HTTP and HTTPS, and a STUN check measures your network. Matches themselves run directly between the two players. The main page tells the story; this page has the details for developers: byte layouts, keys, every command and the code addresses they were found at. Everything beyond Quick Match (relay, rooms, results, co-op, menus) is on How the online functions work.

Gate exchange

Correction (2026-11-04). The 152-byte "hello" is not a key exchange. It is an ordinary CMD_GET_SVRLIST request, and the client speaks first. The RC4 / dlcp code found earlier is real, but it is a different link (see Not the gate). The old "reply must be 16 bytes" result was a side effect: our reply was decoded as a command, and a 16-byte body produced a garbage length that crashed the client's MessagePack reader.

Login sequence (live)

  1. Player id (our mod 0.3.0+, not the game): before the game's first frame on each tcp/10000 connection the mod sends one line PESID1 <32 hex>\n (40 bytes), a hash of a random secret in pes2021-online.ini and the PC's MachineGuid. It does so only when /mod/hello answered version 2 or newer. Mod 0.4.0 asks v=3; a version-3 server gets PESID2 <32 hex> math1\n instead, meaning the game uses the mod's own sinf/powf/atan2f/qsort… (Microsoft's and Wine's differ in the last bits, which ended a Windows-vs-Proton match at kick-off with SYNC_FAILED / RMYN393), and matchmaking pairs only games with the same setting. Mod 0.5.0 adds coop1 (PESID2 <32 hex> math1 coop1\n) when its Online Co-op fix is in (two hooks on the game's 1.01.00 co-op code); co-op matchmaking pairs only such games. The server stores accounts by it (m:<id>) instead of the game's username, which comes from the Steam ID and is the same in every copy that doesn't run through Steam. The game's frames start with 0x5b (XOR), so the line can't be mistaken for one.
  2. GATE (tcp/10000): CMD_GET_SVRLIST → CMD_GET_URLLIST → CMD_GET_SVRVERSION → CMD_GET_SVRTIME → CMD_GET_EULA_NATION_LIST → CMD_GET_EULA_NATION_CODE → CMD_DISCONNECT logoutstat=MOV. A second gate session fetches CMD_GET_GLOBALINFOTITLELIST. LIVE
  3. First run only: Country/Region picker (from our nation list) and Terms of Use screen (documents opened via ShellExecute on URL-list entries EULA_*). Persisted locally once a full login succeeds. LIVE
  4. HTTP POST to the URL-list entry AUTH_STEAM: form msgid=CMD_AUTH_STEAM&rqid=0&urltype=AUTH_STEAM&steamid=…&package_type=DEFAULT; reply is a raw msgpack map (JSON is rejected with C_GKCC_0008_200). LIVE
  5. ACCOUNT (same socket, svrtype ACCOUNT): CMD_SEND_HEARTBEAT, CMD_GET_CHALLENGECODE, CMD_LOGIN {username, hash, platform PC, sku}, CMD_SEND_PSID, CMD_GET_PLAYER_DATA (has_data NO → "Create User Data" screen → CMD_CREATE_PLAYER {name}), CMD_SET_LANGUAGE, CMD_DISCONNECT MOV. LIVE
  6. MENU (new connection): CMD_LOGIN, CMD_SET_CURRENTPLAYER → reply carries key (base64) + key_size; the client switches its Blowfish key to base64-decode(key) for every later frame. Then CMD_GET_STORE_PRODUCT_LIST, CMD_GET_GP_ACHIEVEMENT, CMD_GET_STORE_TRANSACTION_STATE, heartbeats every 30 s. LIVE
  7. Live update: LiveDataSetFlow (0x1420ac3f0) POSTs CMD_GET_DLC_FILELIST (file_type LIVEDATA, region REGION_ALL) to the URL-list type FLOW. Without a FLOW URL it fails locally ("New data asset download unsuccessful", then logout FIN). Answering with empty lists and dlc_version "1.00" gives "No new Live Update available" and the client proceeds. LIVE
  8. Online main menu: CMD_GET_GLOBALINFOTITLELIST, CMD_GET_PRIVATEINFOTITLELIST, CMD_GET_DMM_PLAYERINFO, CMD_SEND_LOG. LIVE
  9. The client caches the URL list for the whole game session; URL-list changes need a fresh title login. LIVE

Wire format

NclMio frame LIVE STATIC

kindu16 BE
lenu16 BE
sequ32 BE
md5(header + body)16 B
bodylen B (≤ 0x410)

The whole frame is XOR'd with the repeating key 5b 9f 2e 64 (constant at 0x143515acc). The md5 covers the plaintext header and the body before XOR. Parser: 0x1418548c0.

Messages larger than one frame continue in the frames that follow; the server reassembles them (seen when entering myClub, about 1.7 KB). Exact layout of the continuation frames INFERRED: the server accepts either plain continuation or a repeated 9-byte header, and logs which one the client used.

NAT test ("Testing network environment")

  • Resolves ntl.service.konami.net, sends 32-byte UDP probes to port 3478, opens TLS to port 443, and does UPnP discovery against the LAN router. LIVE
  • Its UDP socket is bound to the network interface, so it cannot reach 127.0.0.1 — the redirect target must be the machine's LAN address. LIVE
  • Probe order: (1) 32-byte Binding Request with vendor attr 0xF000 (8 bytes: 05730000 00000002); (2) TLS to port 443 with SNI ntl.service.konami.net (then POST /ntl/api/GateInfo.php, see below); (3) 64-byte Binding Requests every 5 s with vendor attrs 0x9090 (24 B, starts 10000001) and 0x9091 (12 B, 00010104 00000000 <counter>). The keepalives need more than a plain Binding Success (see next item). LIVE
  • A plain Binding Success (XOR-MAPPED + MAPPED, same tid) is accepted for the 0xF000 "MappingTestIA" probe. The 0x9090/0x9091 packets are post-test keepalives (RP_P2P_HEADER / RP_RELIABILITY); a new serial every 5 s means they are being answered. Don't send OTHER-ADDRESS unless a real alternate IP:port exists. LIVE
  • GateInfo.php: POST https://ntl.service.konami.net/ntl/api/GateInfo.php, User-Agent NTL HttpModule/0.1, body req={"titleCode":"PES2021",…}. WinHTTP default certificate validation (no pinning). The mod sets WINHTTP_OPTION_SECURITY_FLAGS (ignore unknown CA / CN / date / usage) on requests whose connection was opened to one of the four ntl*.service.konami.net names, and on nothing else. (The earlier join scripts instead trusted a private CA name-constrained to those four names.) Reply is text lines: STATUS: 200, API_STATUS: 0, LOG_ACTIVE: 0, SERVER_TIME: <unix>. LIVE

Matchmaking — live

  1. eFootball → NAT test → live-update check → CMD_SEND_IPANDPORT_NTL (host_addr blob with raw sockaddr) → CMD_GET_GAME_TEAM_LIST, CMD_GET_SERVER_ENV, CMD_CHECK_CHEAT, CMD_GET_URGENT_ANNOUNCEMENT (online_mode QUICK), CMD_GET_MANNER_WARN. LIVE
  2. Select Team → CMD_GET_QUICKMATCHOPTION → "Matchmaking Settings" → Go to Matchmaking → CMD_GET_MAINTENANCE_INFO, CMD_START_MATCHING {matching_type OC_QUICK, has_guestplayer, guest_info}. LIVE
  3. Both clients show "Matchmaking — Searching for an opponent" and never poll; the server paired them ("MATCH FOUND room 1"). LIVE
  4. Server push CMD_WATCH_MATCHING (kind 0x60, seq 1, rqid 0): pushes are routed by msgid only to watches the client registered (0x141239840 / 0x1412395f0). The key field is matching_state: FINISH → match accepted; missing → ignored → 300 s timeout = error EYRH763 (line 763 of the quick-match task). Members: blobs {pid, pname, is_owner YES/NO, matching_order, host/reflexive/relayed_addr, ntl_nat_type}. LIVE
  5. Game relay: CMD_GET_GAMERELAY is an HTTP web-API call to URL-list type GET_GAMERELAY (then GET_TURN_SERVER_LIST as fallback). Missing type → instant local failure ER_MATCHING_RETRY. We now serve all 53 URL types from the client's enum (0x14021ee70), short paths to fit one frame. LIVE
  6. Peer signalling: clients send CMD_SEND_SYNC_NOTICE / SEND_SYSTEM_NOTICE {pid_list, data} ("1,", "END:pid=2;time=…"); the server must relay each as CMD_WATCH_SYNC_NOTICE / WATCH_SYSTEM_NOTICE {data} to the listed pids. With relay on, both report CMD_SET_GAMERELAY_CHECK_RES {game_sycom P2P, error_code NOERR} and exchange UDP directly; server pushes CMD_WATCH_GAMERELAY_CHECK_RES {error_code NOERR}. LIVE
  7. Then CMD_SEND_MATCHING_RESULT {member, vs_member, game_sycom P2P}, CMD_SET_GAMEMEMBER, CMD_SET_GAMEMEMBERENV {envlist pid/side/sideLeader}, CMD_GET_MATCHID, CMD_CHANGE_GAMEPHASE TEAMSELECT → MATCHMENU (online pre-match menu, shared countdown) → both players Kick Off → both GAMELOAD. LIVE
  8. Sides: every WATCH_MATCHING member blob needs side = HOME (owner) / AWAY. Without it the HOME team is never filled and team-data sync aborts with MMGC_0002 (MultiplayCmdTeamDataSync.cpp line 2). LIVE
  9. Team list: CMD_GET_GAME_TEAM_LIST must return the selectable clubs as blobs {team_id, team_class, division_point}; ids are the game's internal DB ids (100 Man Utd, 101 Arsenal, 108 Barcelona, 114 PSG, 116 Ajax, 120 Juventus, 127 Bayern, 131 Celtic). Empty list → no team to pick. LIVE
  10. Server environment: CMD_GET_SERVER_ENV timeouts must be real values (load_timeout 180, long_outofplay 120, init_not_end 240, cmd_lack 180 …). Zero-filled defaults made the client abort instantly with LOAD_TIMEOUT (QVHE1459, GameModeMatchListenerMatch.cpp) and then crash while tearing down match::Online. Lesson: an unhandled command gets a bare {result: NOERR} so the client keeps its own defaults — never zero-filled fields. LIVE

Match — live

  1. After MATCHMENU both clients Kick Off → CMD_CHANGE_GAMEPHASE GAMELOAD → ENTRY → 1ST. Gameplay itself is peer-to-peer UDP between the clients; the server only sees phase reports and events. LIVE
  2. Phases reported (each with gtimer, the game clock): DATASYNC, TEAMSELECT, MATCHMENU, GAMELOAD, ENTRY, 1ST, 1ST_15MIN, 1ST_30MIN, BREAK1 (half-time), 2ND, 2ND_15MIN, 2ND_30MIN, then the end of the match. A bare NOERR reply to each is enough. LIVE
  3. Events during play: CMD_ADD_FOUL (fouls, yellow cards); both clients report the same events, and their clocks stay in sync. LIVE Goals are reported as CMD_ADD_SCORE {goal_side, goal_player_pid, assist_*, gtimer}; there is no CMD_ADD_GOAL in the client (details). LIVE
  4. Full time: both clients send CMD_CHANGE_GAMEPHASE {phase END, gtimer 94107} (90 min + stoppage), then show the highlights reel and match records. Post-match reporting: CMD_SET_PLAYDATA_MATCH (HTTP, URL type PLAYDATA_MATCH, JSON play_data), CMD_SEND_STATS_DATA {match_id, stats[] per side}, CMD_SEND_GAME_RESULT {game_phase END, side, home/away_score, home/away_team_id, abnormalend_reason NOERR, …}, CMD_REQ_GAMEADDPOINT, CMD_LEAVE_ROOM. A bare NOERR to each returns both players to the menu; a new Go to Matchmaking pairs them again straight away. Verified with a complete 90-minute match on 2026-11-04 (18:20–18:52, Arsenal v Arsenal 0–0). LIVE
  5. The player who leaves the post-match screens second reports DISCONN_P2P / GNCX_0003 (OnlineModeMultiplay.cpp): the peer link has already closed. The result is still recorded normally. LIVE
  6. Abnormal end: CMD_SEND_ABNORMALEND {reason, error_code}. Seen reasons: NO_OPERATION (a player gave no input for about 70 s (live, 2026-11-05); this is the game's AFK rule), DISCONN_P2P (peer link lost), LOAD_TIMEOUT. With real server-environment timeouts, both games returned to the menu without crashing (the LOAD_TIMEOUT crash in the matchmaking section happened only with zero timeouts). LIVE

Error codes

On-screen codes such as EYRH763 or MMGC_0002_0_… encode the source file and line: the four letters are a hash of the .cpp basename (characters bucketed by index mod 4, each bucket summed mod 26 + 'A'), followed by the line number. notes/re/errcode.py matches the letters against every source-file name in the binary's strings.

Deployment

  1. Host (Linux): run.sh downloads the newest program from the latest GitHub release (PyInstaller, built by .github/workflows/program.yml) and runs pes2021-server install: a systemd user service, an apps-menu entry, then the admin page. Updates (checked against the release's SHA256SUMS and test-run), restart and stop are on the admin page. No configuration: netsetup.py finds the LAN IP, asks the router for its external IP and opens TCP 80/443/8080/10000 + UDP 3478/7600 over UPnP IGD (renewed every 30 min, removed on stop), checks the public IP against a what-is-my-IP service to detect CGNAT, and prints the admin page address and password. It also looks for PES2021.exe (Steam libraries, ~/Games) and their Wine prefixes, for the admin page's one-click install (on Windows, Steam's registry entry). LIVE
  2. Per-client address: SVRLIST / URLLIST / GAMERELAY carry the server address. Without a pinned PUBLIC_IP, a client from a non-global address (LAN, Tailscale 100.64/10, loopback) gets the local address its TCP connection reached (sockname); LIVE An internet client gets the public IP, so one server can serve LAN and internet players at once (no internet client tested yet). INFERRED
  3. The mod (server/mod/, built by the image's first stage with MinGW): a dinput8.dll proxy (exports forwarded to the system DLL) that hooks ws2_32 getaddrinfo / GetAddrInfoW / GetAddrInfoExW / gethostbyname for the 6 Konami names, and winhttp WinHttpConnect / OpenRequest / SendRequest for the NTL certificate exception, plus WinHttpCloseHandle (to forget closed handles) and user32 CreateWindowExW / CreateWindowExA (to start the server lookup, or the Shift box, when the game's first window opens). Hooks are MinHook detours in the system DLLs; the game's own code is not touched. Loaded under Proton via WINEDLLOVERRIDES="dinput8=n,b" or the per-program registry override [Software\\Wine\\AppDefaults\\PES2021.exe\\DllOverrides] "dinput8"="native,builtin", which the admin page writes into the prefix's user.reg. LIVE
  4. Server identity: an Ed25519 key in the data volume. /mod/dinput8.dll writes the public key and the server's addresses into a 2 KB reserved section of the DLL (.pescfg). Before using an address the mod GETs /mod/hello?n=<random nonce> and checks the signature (Monocypher); to find the server again it fetches a signed /mod/note (time + addresses) and ignores notes not signed by that key or older than the last one seen. Tested in the game: fresh download, dead web link plus wrong IP, forged note rejected. LIVE
  5. The server still keeps the private CA (name-constrained to the four NTL host names) for players set up with the older join scripts (/join, /ca.crt); the mod doesn't use it.

How it was tested

Every finding marked LIVE was checked against the game's original 1.01.00 executable, run directly under Proton on Linux (a run started through the Steam client is still pending). A recorded log of real client requests is replayed through the server's handlers offline and each reply is validated against the reply formats extracted from the game (server/test_ncl.py; the published repo replays the captured first frames in notes/re/captures, the full recorded log stays local). End-to-end runs drove two copies of the game on one Linux PC through login, the network test, matchmaking and complete 90-minute matches. The local test harness itself is not part of the published repo.

How we found it

  1. Wine's own debug channels (WINEDEBUG=+seh,+winsock) showed the client crashing in memcpy called from 0x1418568bb right after reading our reply.
  2. That function is the NclMio decoder: it builds a message object, decrypts the body, and switches on kind.
  3. The crypto factory 0x141856610 allocates a 0x1050-byte object for the easy tier — the size of a Blowfish context.
  4. 0x14116eeb0 installs a 56-byte key from .data when none is set.
  5. Blowfish-ECB with that key turned the captured "hello" into readable MessagePack.

Open questions

Every remaining online function is now mapped from the game's code on a separate page, How the online functions work: what each command does, what the server must send, all 433 commands and all error codes. What's left to build:

  • Relay fallback: the game uses a standard TURN relay over TLS, but only when CMD_GET_TURN_SERVER_LIST returns servers. We return none, so there's no fallback yet. The UDP 7600 "game relay" is a different, Konami-only mode that Quick Match never uses. Details STATIC OPEN
  • Results: final scores are stored, and live goals now come from CMD_ADD_SCORE (there is no CMD_ADD_GOAL). The rating verdict (CMD_WATCH_GAMEADDPOINT) is never pushed, so one player waits 20 s after each match. Details OPEN
  • Rooms for playing a chosen friend, co-op, divisions, myClub and events: protocol mapped, not implemented. OPEN
