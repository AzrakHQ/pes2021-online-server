How the online functions work

A reference for everyone building on this server: every online function of eFootball PES 2021 (1.01.00, Steam), worked out from the game itself. It covers what each command is for, how the game uses the reply, and what a private server has to send. It continues the technical write-up, which covers the wire format, login and Quick Match. Static analysis of the game binary and our own test logs, 2026-11-05.

In plain words: the game knows 433 server commands. Our server implements 33 and answers 40 more with a plain "OK". This page explains what the rest do, which of them matter, and what our server should change. Every claim has a tag saying how sure we are, and an address in the game's code where it can be checked.

What changes for our server

The findings that change server behaviour, most important first. Each one links to its section.

  1. No relay fallback exists today. The game only uses TURN when GET_TURN_SERVER_LIST returns servers; we return none. Run coturn (TURN over TLS), answer the list with credentials and certificate, and forward SEND_TURN_ADDRESS_DATA to the opponent as a WATCH_TURN_ADDRESS_DATA push. The UDP 7600 "game relay" isn't a fallback and can go. Connecting the players → DONE Built, off by default (TURN=1): a small TURN server inside our program (TLS 5349, UDP relay 49160–49179 opened with UPnP, RFC 8016 mobility, which the game asks for), a self-signed certificate naming the server's addresses, TURN REST credentials, and byte-exact address forwarding. Traffic between two players' relays is handed over inside the program, so no router loopback is needed. Connecting the two players: NAT traversal, TURN relay, game relay

In plain words: the two games try to reach each other directly (UDP hole punching). If that fails, the game can fall back to a standard TURN relay over TLS, but only when the server hands it a TURN server list. Our server currently returns an empty list, so there is no fallback at all, which is why players in different homes can get "Failed to connect with opponent". The "game relay" on UDP 7600 is a different, Konami-only relay mode that Quick Match never uses.

How a match connection is set up

  1. Network test at mode entry: the NTL library ("NTL 1.11.11-Windows64") tests the NAT against the STUN server (UDP 3478) and GateInfo.php, tries UPnP, then reports its addresses with CMD_SEND_IPANDPORT_NTL {host_addr, reflexive_addr, relayed_addr, ntl_nat_type}. LIVE
  2. Pairing: CMD_WATCH_MATCHING member blobs carry each peer's NTL addresses. LIVE
  3. Match session task (OnlineModeTaskMatchSession.cpp, fn 0x1411430b0, state in [task+0x70]): GET_SERVER_ENV → GET_TURN_SERVER_LIST (states 9/0xa) → SetConfig() (state 0xb) → CreateMultiplaySession (state 0x11; also starts ConnectTurnTask and the WATCH_TURN_ADDRESS_DATA watch) → wait for the link (state 0x15) → revision check → connected (0x1a). Errors go to state 0x17. STATIC
  4. Connection strategy (factory 0x1411aa730) depends only on whether the TURN list is empty. The NAT type is not consulted: STATIC
    • empty list (our server today) → P2pFullMesh: NTL hole punching only, no relay;
    • non-empty list → P2pFullMeshWithTurn with P2pTurnIoFailover: direct path plus a TURN path, switching between them. (Debug tunables turn_mode / direct_online_turn_mode default to this.)
  5. When the link doesn't come up in about 30 s, both games report CMD_SET_GAMERELAY_CHECK_RES {error_code ER_MATCHING_RETRY, failed_reason 2}. LIVE The match task retries once after 15 s (cmp rax,0x3a98 at 0x141143ccd). Link results: 1 ok, 2 "Revison check TIMEOUT", 3 "Revision error", 4 "DATAPACK error", 5 "Other user disconnected". STATIC

CMD_GET_TURN_SERVER_LIST: TURN servers and credentials

  • Transport: HTTP (URL type GET_TURN_SERVER_LIST). Requested every match, twice per client, once by the match task and once by ConnectTurnTask. Not at login. LIVE
  • Request: pid, turn_account_param (= the pid as text), turn_time_limit (always 60). The game never uses either value itself. They look like hints for time-limited TURN credentials. STATIC INFERRED
  • Reply (parser 0x141e4e650, stored in onlinesystem::ParameterTurn): STATIC
    • turn_server_list: an array of inline maps (not nested blobs) {zone NUM, address STR, port NUM, tls_port NUM}. Entries with port or tls_port = 0 are dropped. Only tls_port is used to connect; port only has to be non-zero. Any zone works: servers are grouped by zone, and failed ones are skipped for a while.
    • id / pw (STR): TURN long-term username and password. If either is empty, TURN is silently skipped.
    • server_certificate (STR): base64 of a DER X.509 certificate (a PEM body without its BEGIN/END lines works), added to the TLS trust store. server_certificate_data_size (NUM) = number of DER bytes. Invalid DER aborts the TLS session.
    • origin (STR, optional): passed to the TURN client config (ORIGIN attribute, RFC 7635 style).
  • Bare {result:NOERR} (today): empty list → no relay; nothing errors. LIVE

The TURN client: Konami "ktc-0.0.0"

  • A standard RFC 5766/8656 client (namespaces ktc::session, ktc::socket, ktc::lib::TlsSession, OpenSSL 1.1.0i): Allocate / Refresh / CreatePermission / ChannelBind, 401+nonce long-term auth, 438 stale nonce, 437 allocation mismatch, 405 mobility forbidden. Defaults: lifetime 60, 10 retries. STATIC
  • Transport: TURN over TLS on TCP (RFC 5766 §2.1) to address:tls_port. A second UDP/DTLS "dual route" leg opens only if the server returns a host:port,… string (a Konami extension; coturn's SOFTWARE value doesn't match it, and no-software-attribute removes the risk). STATIC
  • The switch-over thresholds (ChangeoverToTurnReceiveIdleTimeMsThreshold, TurnNetworkIoConnectionTimeoutMs, TcpFallbackEnable, …) come from the game's local multiplay parameter data, not from the server. STATIC
  • The NTL library has its own, separate TURN client (ntl::TurnClient), which would fill relayed_addr. That field is all zeros in every log, and no code path configures it, so treat it as unused. INFERRED
  • m_TurnQuality* / TURN_QUALITY_* / TURN_CHANGEOVER_* / ROUTE_TCP_MS strings are keys of the post-match network statistics record. They are telemetry, not settings, but useful later to see whether a match used TURN. STATIC

CMD_SEND_TURN_ADDRESS_DATA → push CMD_WATCH_TURN_ADDRESS_DATA

  • After its TURN allocation succeeds, each client sends {pid, address, address_data_size} (gate, svrtype MENU). The address blob is the serialized relayed address; its byte format isn't decoded, so treat it as opaque. A non-NOERR reply makes ConnectTurnTask fail. STATIC
  • The server must push CMD_WATCH_TURN_ADDRESS_DATA {result:"NOERR", address, address_data_size} to the opponent with the bytes unchanged (msgpack str, like sa_data). The push has no pid field. The client then creates a permission and channel to that address. STATIC
  • CMD_WATCH_PUNCHING_DATA {host_addr, reflexive_addr, ntl_nat_type} is used only by lobby/room flows, not Quick Match. STATIC

CMD_SEND_IPANDPORT_NTL and a likely cause of cross-home failures

  • sa_data = 14 bytes: port (big-endian), 2 zero bytes, IPv4, 6 zero bytes. address_family 1 = IPv4, 0 = empty. ntl_nat_type is a packed descriptor (seen 1 before the test, 0x10307533 after a good test); its bits aren't decoded. LIVE
  • reflexive_addr is whatever our STUN server sees. When the server runs in one player's home, that player's game reaches it over the LAN, so its "public" address is its LAN IP (logs: host == reflexive == 192.168.1.100). The friend in another home is then given an address it cannot reach. This alone can explain "Failed to connect with opponent" between homes, even when both routers would allow a direct path. LIVE INFERRED
  • Cheap fix without TURN: when a LAN-side player is paired with an internet player, rewrite the LAN player's reflexive IP to the server's public IP and keep the port. This works on routers that preserve source ports. TURN is the robust fix.

CMD_GET_GAMERELAY and the "game relay"

  • game_sycom selects the transport: "P2P" → mode 1, "SC" → mode 2 (server/client through Konami's game relay), anything else → 0. Only with "SC" are ip_addr/port kept; otherwise they're cleared. That is why the client's CHECK_RES shows an empty gamerelay. STATIC LIVE
  • "SC" uses MultiplaySessionStrategyCsClient, a full client/server relay with Konami's own protocol (kps msp over dlcp, see transport layers). It is not a TURN-style fallback. Our UDP 7600 has never received a packet. LIVE
  • GET_GAMERELAY_QUALITYCHECKLIST, SET_GAMERELAY_QUALITY, SET_GAMERELAY_MATCH_QUALITY and the LOCAL_GAMERELAY commands measure or select relays for SC mode and the lobby's "LocalGamerelayDialog". A bare NOERR is fine for all of them. STATIC
  • CMD_SET_GAMERELAY_CHECK_RES {pid, game_sycom, error_code, gamerelay{…}, failed_reason, is_special_match_confirm} is each client's verdict on the connection. Push CMD_WATCH_GAMERELAY_CHECK_RES {error_code}: NOERR only if both sides reported NOERR, otherwise ER_MATCHING_RETRY, so both go back to searching. INFERRED

What our server should do

  1. Run coturn on an internet-reachable address: tls-listening-port=5349; a non-zero but unused listening-port (3478 is our STUN); a self-signed cert whose IP SAN is the advertised address; lt-cred-mech; user=pes:<password>; realm=pes2021; external-ip; a UDP relay port range forwarded on the router. Behind a home router, coturn relaying between its own two allocations needs NAT hairpinning; a VPS avoids that. INFERRED
  2. Reply only when TURN is configured: {result:"NOERR", turn_server_list:[{zone:1, address:"<public IP>", port:3479, tls_port:5349}], id:"pes", pw:"<password>", server_certificate:"<base64 DER>", server_certificate_data_size:<len>}. For time-limited credentials: id = "<expiry>:<pid>", pw = base64(HMAC-SHA1(secret, id)) with coturn use-auth-secret, and an expiry of hours (refreshes happen during a 90-minute match).
  3. Forward SEND_TURN_ADDRESS_DATA to the opponent as a WATCH_TURN_ADDRESS_DATA push, and queue it if the room isn't ready.
  4. Keep game_sycom:"P2P". The UDP 7600 placeholder can go.
  5. Rewrite the host player's reflexive address when the opponent is remote (see above).

Still unknown: whether ktc verifies the certificate when none is sent (send one); REQUESTED-TRANSPORT (UDP vs TCP relay); the address blob format; whether a dead TURN server breaks the match or just leaves P2P. One live run against coturn with verbose logging settles all four.

Match flow: setup, in-match reports, end of match

In plain words: after pairing, each game runs a "match session" task. It gets a match id, waits at a sync barrier, reads timeouts, gets the TURN list, then opens the player-to-player link, using two notices relayed by our server as a rendezvous. During the match, both games report every phase, foul and goal. The server only has to answer "OK", and must never answer ERR_CHEAT.

Peer notices relayed by the server

All three SEND commands carry {pid_list_num, pid_list[int], data STR}; the pushes carry {data}. The client never checks who sent a notice except through what's inside data. STATIC

  • SYNC_NOTICE = match-session barrier. data = "<pid>," for each other member. The receiver pops one entry and ignores its contents. pid_list grows by one copy per match: the game never clears the vector it's built from ([2], [2,2] … [2,2,2,2,2,2] in our logs). If the server relays every copy, stale entries make the next match's barrier pass instantly. Harmless, but not real synchronisation. LIVE STATIC
  • SYSTEM_NOTICE = P2P connect rendezvous (thread 0x1411d9620). data = "START:pid=<sender>;time=<unix s>;" or "END:…". Each handshake waits up to 30 s for a matching entry at the head of the queue, and the parser doesn't drop a non-matching head. One duplicate or stray notice therefore blocks the handshake and the P2P connect fails. Relay data byte for byte: each side builds the session tag "pid-pid-…-min(own time, peer time)" from time= and passes it to the NTL connect (0x1411d81d0), so altered times make the tags differ. STATIC
  • NOTICE = JSON notices for rooms (not Quick Match): {"notice_key": …} with MOMROOM_START_COUNTDOWN {from_pid, reason, count_zero}, MOMROOM_RESULT_TIMEOUT, MOMROOM_REQ_RESULT_TIMEOUT {from_pid, roomid}, ROOM_SHARE_INFO {from_pid, has_team_data, team_power, chemistry, team_id, team_name}, SYNC_PROGRESS {pid_list}. Keys exist with no builder found: MOMROOM_CANCEL/REQUEST_COUNTDOWN, MOMROOM_SEND_XSESSION_INFO, MOMROOM_CONNECT_COMPLETE, QUICK_PING_RES. STATIC
  • Server rule for all three: take set(pid_list) − {sender}, deliver each push exactly once per target, keep the order (START before END), never inject extra notices.

Liveness probe and reconnect

  • CMD_WATCH_CHECK_ALIVE_PLAYER is a server push ("are you still there?"). The client answers with SEND_ALIVE {pid, reason} (NOERR, DISCONN_SC = P2P link down, DEGRADE_SC = server path degraded) and SEND_ALIVEPLAYER {pid, pid_list} listing the peers it still hears. Lobbies and rooms: playing a chosen friend

In plain words: the game's "Online Match Lobby" is fully built into the client. You pick a lobby, then a sub-area ("block"), then create a 1 vs 1 room with an optional password, and your friend joins it from the room list. Once both press Entry, the owner's game starts the match, and from then on it's the same match flow as Quick Match. The server has to keep rooms and push room and player lists. Platform invites and the follow list don't give a usable path to a friend's room; room list + password is the practical way.

Two lobby products STATIC

  • Free lobby (menu freelobby, game mode LOBBY1VS1, task TaskLobbyRoomMainFree): 1 vs 1 rooms. max_players = 2 is hard-coded (0x1410e86bb). This is the one we need.
  • Multi / MOM lobby (multilobby, MOMLOBBY): several humans per side, 11-a-side room screen, countdown notices, best player, position rating. It shares about 90 % of the protocol.
  • Hierarchy: menu "Server" = lobby (GET_LOBBYLIST/JOIN_LOBBY) → menu "Lobby" = block (GET_BLOCKLIST/JOIN_BLOCK, a sub-area with its own room list and player cap) → room.

Three kinds of commands

  1. Plain request/reply (CREATEJOIN_ROOM, ENTRY_GAME, …).
  2. WATCH_* = pure server pushes. The client registers a local watch and never sends a request (no RX of any WATCH_* in our logs). Push with kind 0x60, rqid 0. LIVE STATIC
  3. REQWATCHL_* = request + list subscription. The request carries arguments (room_id) and is answered; later pushes with the same msgid update the list. Safe behaviour: answer and also push. INFERRED (strong)

The list protocol for all REQWATCHL_* STATIC

Merger 0x1411c1340. Every list reply or push has list_key_name, list_type and list_data (an array of msgpack blobs):

  • RELOAD clears the cached map and inserts every element; ADD/UPDATE (re)insert; DEL removes. An empty or missing list_data changes nothing, even with RELOAD, so to clear a list you DEL each element.
  • The key is the field named by list_key_name inside each element (room_id for room lists, pid for player lists). It must be a msgpack int; a string or double key becomes 0 and the elements collide.

Co-op (2v2, 3v3) and spectating

In plain words: co-op reuses the 1v1 match machinery. The game opens one player-to-player session between all 4 or 6 players (every player connects to every other). The server's new job is matchmaking: first form each side ("group matching"), then pair two sides ("co-op matching"), using two pushes. Spectating is store-and-forward: the players upload their match while it's played, and viewers download it in encrypted chunks over HTTP.

Fair play, news and the online menus

In plain words: at online login, the game sends two checksums of its player database. If two players' databases differ (edited stats, a different live update), their match fails with "DATAPACK error" after connecting, so the server should only pair players whose checksums match. The game can also show the server's own messages: a pop-up announcement, a news list and a "maintenance soon" warning. Everything else in the menus is safe with a plain "OK".

Transport layers: large messages, the AES tier, dlcp, and the player-to-player link

In plain words: the game has three network stacks. (A) The server connection we already speak, which also has an unused AES mode. (B) The encrypted UDP link between the two players. (C) The NAT-traversal messages. Only one thing here needs a server change: messages bigger than about 1 KB have to be split into fragment frames.
(A) Server link (gate / ACCOUNT / MENU, TCP 10000)
    onlinesystem::Client → fox::ncl NclMio (Blowfish tier)  or  NclEnhancedMio (AES-256 tier) → msgpack
(B) Player ↔ player match link (UDP, direct or through TURN)
    onlinesystem::P2pFullMeshSession / CsClientSession / ObserveSession
      → kps::msp (multi-session protocol) → kps::domain::LlDomain + Clltcp (connections)
      → kps::lltcp FastTcp / ScalableTcp (reliability, pacing) → kps::dlcp (key exchange + RC4 records)
      → onlinesystem::NtlNetworkIo / P2pTurnIo* → ntl → UDP socket
(C) NAT traversal (ntl, cobra\NatTraversal\NTL): STUN-format messages with Konami methods/attributes

The "enhanced" AES tier (NclEnhancedMio / NclCryptAes)

  • Not tied to a server type. It's a global tier: every send uses AES once the client holds a 32-byte key (cmp [daemon+0x144],0 at 0x141216c75). STATIC

kps::dlcp: security of the player-to-player link

  • Every Clltcp connection in an LlDomain owns a dlcp link (vtable 0x142bc53a8 slots 13/19 → LinkController 0x14203c730). So dlcp protects the UDP match link between the players, and would also protect an SC relay or observer link. STATIC
  • Key exchange (SimpleExchangeKeyExchanger): a ≤4-byte token and a 16-byte reply, both RC4 under the static key a977d392 db0e55b9 9d1641c2 d4f82739 (.rdata 0x142bcaf10). The 16 bytes become the session key. Direction is INFERRED.
  • Record: [hdr u8][checksum u16 BE][payload], RC4 with the session key. hdr bit 7 = link flag, bit 6 = zlib (compress2 level 9), bits 0–5 random. The checksum covers the record with the checksum field zeroed. STATIC
  • Sequence and ack live one layer up, in kps::lltcp (FastTcp/ScalableTcp congestion classes, pacing, loss/dup/reorder counters). UNKNOWN
  • Our server never needs dlcp for P2P matches. A TURN relay carries it opaquely. Only an "SC" relay endpoint or an observer would have to speak it.

The game database: players, teams, rosters

In plain words: every player and team the game knows is in a set of small files inside the game's archives. They're compressed but not encrypted, and now fully decoded. The proof: recomputing the game's own login checksums from these files gives exactly the values our test clients sent. With this, the server can turn the player and team ids in match results into names, build squads, and tell two players why their data doesn't match.

  • Coach, Country, Stadium, Competition, CompetitionEntry, Derby, Tactics, PlayerWeekly and TeamWeekly are described in notes/re/functions/db.md.

What the login checksums really are LIVE STATIC

  • param_check_sum = for each player, (id & 0xffff) + the 108 parameters + (height & 0xff) + (weight & 0xff) + condition, summed into 4 accumulators and XOR'd with a fixed key. entry_check_sum = for each team, team id + Σ(player id + shirt number).
  • Recomputed from the stock update-pack files: 25D6DFBB091E75D525E090F993DBAE73 / 1E21A82F1DFF00C9DBE591735FF8746A, exactly what both test clients sent. So both ran the unmodified update-pack database, with no edits and no live data. A game without the update pack (dt10 only) sends 25BC6828… / 1E8FB88B… and would fail the revision check against an updated player.
  • The "condition" term is the player's weekly form from PlayerWeekly.bin, but only after a live update has been applied (DB live-data mode 1, set by LiveDataSetFlow). Otherwise it's the constant 5. So delivering live data changes every player's checksum: all players must get the same live data.

Saves and the option file

Saves live in Documents\KONAMI\eFootball PES 2021 SEASON UPDATE\save\ (types EDIT, SYSTEM, LIVE, …). They're encrypted with an MT19937-based XOR stream (0x14140e0f0), keyed from 64 header bytes at +0x100. Where the master key comes from wasn't traced, and no save files were read. Edit data overrides the database, so an edited option file changes the checksums. STATIC

Using it

notes/re/functions/tools/pesdb.py reads the CPKs directly (update pack first): checksum (both sums, also the live-data variant), player <id>, team <id>, dump out.json. For the server, it gives names for the ids in SET_PLAYDATA_MATCH and line-ups, squads for vs-CPU co-op and a myClub-lite, and a way to name the cause when two players' checksums differ (missing update pack vs edited data).

Live Update: how the game downloads new data

In plain words: at login, the game asks the server whether there's new "Live Update" data. If there is, it downloads one file over plain HTTP, checks it against a SHA-256 hash the server sends, saves it, and loads it on top of its data, the same way it loads the update pack. Our server could use this to give every player on it the same rosters and form, so their data never mismatches. Konami's server did exactly this, and the game expects nothing more.

Three kinds of downloadable data STATIC

All three are ordinary CRI CPK archives, loaded on top of the base data (driver livedata::LiveDataSetFlow, LiveDataSetFlow.cpp, error prefix SGJC, update fn 0x1420ac3f0):

The sequence

  1. Data pack gate: the game's update-pack version (version_dp.bin in dt80 = "1.00" | "1.01.00" | "2396" → 100) must not be lower than the server's DLC version, which is GET_SVRVERSION dlc_version (copied to [netmgr+0x68] by 0x1410f08c0). Otherwise ERROR_CODE_DP_VERSION_OLD (SGJC392). Our "1.00" passes. GET_SVRVERSION livedata_version has no reader. STATIC
  2. Ask: CMD_GET_DLC_FILELIST over HTTP to the FLOW URL: file_type=LIVEDATA&region=REGION_ALL&pid=0. Sent at every login and again on entering an online mode, before JOIN_ONLINE_MODE and CHECK_CHEAT. LIVE
  3. Decide: Live Update is new if atoi(dlcfile_list[0].dlc_version) > the version of the Live Update already saved (0 if none). Version strings in the files parse as "a.bb" → a·100+bb, so "1.01" ↔ "101". STATIC
  4. Download: plain WinHTTP GET of the entry's url (https only if the URL says so). It needs status 200, and the body must be exactly size bytes: longer fails, shorter is zero-filled and fails the hash. The limit is 120 s for the whole transfer. STATIC
  5. Check: SHA-256 of the downloaded bytes as 64 lowercase hex characters, compared exactly with hash (mismatch → "wrong hash", SGJC1006). That's the only check: no signature or key. STATIC
  6. Save and load: the raw bytes go into the save slot (save failure → SGJC1102), then get loaded as a CPK at priority 5 (load failure → SGJC1306). Afterwards the edit data (option file) is re-applied on top, so players' own edits stay. A "LiveDataSetDialog" confirms it. STATIC

CMD_GET_DLC_FILELIST reply STATIC

  • Fields: dlcfile_list_count, dlcfile_list, variation_file_list_count, variation_file_list, extra_file_list_count, extra_file_list (parser 0x141d34a90). There is no top-level dlc_version; the one we send is ignored.
  • Each element is a real inline msgpack map (not a nested blob): {name STR, size NUM, url STR, hash STR, dlc_version STR (integer string), required_program_version NUM (ignored)}. Only dlcfile_list[0] is used. extra_file_list_count is trusted as the count, so keep it consistent with the list.
  • Today we send empty lists: no live data → ERROR_CODE_NOT_DELIVERED → one "No new Live Update" dialog per session and CMD_SEND_LOG {title:"LiveUpdate"}, then login continues. Harmless. LIVE

What a Live Update file contains

  • common/etc/version/version_wu.bin: 30 bytes, three NUL-padded 10-byte ASCII fields (content version, required program version, build string; the same layout as version_dp.bin; only the first field is read). Required: without it the client stays at version 0 and downloads again at every login. STATIC INFERRED
  • The database tables the live-data module handles (0x142bd0ec0): PlayerWeekly, Tactics, TacticsFormation, PlayerAssignment, Player, PlayerAppearance, BootsList, PlayerDeleteList, Coach, CoachDeleteList, TeamWeekly, under common/etc/pesdb/ in the usual WESYS format. A full roster update is about 1.5 MB. Team.bin is not in the list.
  • Persistence: the saved file stays across restarts until a higher version replaces it. The Live Update is applied per session by this flow; Variation and Extra files are loaded from boot.

Effect on matchmaking

CHECK_CHEAT is sent after the Live Update is applied, and with live data active the checksum also includes each player's weekly form. So players with the same Live Update get the same checksums, and a player without it (or with an older one) would hit "DATAPACK error" against them. Players report their live-data version in JOIN_ONLINE_MODE livedata_version ("0" today), which the server can compare. There's also an ERR_DIFFERENT_LIVEDATA_VERSION error code, whose on-screen handling is unverified. STATIC LIVE

Publishing our own update (what the game expects)

  1. Build a CPK with common/etc/version/version_wu.bin (e.g. "1.01" | "1.01.00" | a build string) and the changed common/etc/pesdb/*.bin tables. Our tools/pesmod CPK writer produces CPKs the game accepts.
  2. Serve it with HTTP GET at a fixed URL on the server's HTTP port: status 200, exact Content-Length, raw bytes. httpgate.py needs a new route for this.
  3. Reply: {"result":"NOERR", "dlcfile_list_count":1, "dlcfile_list":[{"name":"livedata_101.cpk", "size":<bytes>, "url":"http://<server>:8080/livedata/101.cpk", "hash":"<sha256, lowercase>", "dlc_version":"101"}], "variation_file_list_count":0, "variation_file_list":[], "extra_file_list_count":0, "extra_file_list":[]}. Tuning the connection: proto_opt, failover, NAT type, NAT test

In plain words: every timeout and threshold of the player-to-player link, including how long the game waits for a connection and when it switches between the direct path and the TURN relay, comes from a JSON text the server sends in GET_SERVER_ENV. We send none, so the game uses its built-in defaults. Konami's real values are lost, but our server can now tune them. The NAT type the game reports is never used by the game itself.

GET_SERVER_ENV.proto_opt: the tuning tree STATIC

  • Chain: GET_SERVER_ENV handler 0x141210dd0 → ParameterMultiplay::SetJson 0x141174b20 → JSON parse. It's read again every time a match session is created (CreateMultiplaySession 0x1411aa730). Invalid or missing JSON (our "NotImplement") is harmless: all defaults stay. A hash of the text is reported back in the post-match stats (PROTO_OPT_HASH).
  • Shape: { "<profile>": { "<group>": { "<key>": value } } }. The profile is "P2P" for normal matches ("CS" for the game relay, "P2P_ADHOC" for direct online). A level profile "P2P_HIGH_LEVEL" / "_LOW_LEVEL" / "_GIVE_UP_QUICKLY_LEVEL" overrides it key by key. Which level Quick Match uses is unknown, so put values in "P2P". Integers must be JSON integers.

When the game switches between direct and TURN STATIC

P2pTurnIoFailover (only when a TURN list is sent) starts on the direct path. It moves to TURN, while the TURN route is up, when: the direct link isn't connected (reason 1); the direct link has been congested for over 10 s (reason 3); or TURN is receiving but the direct link never received (reason 4) or has been silent for 7.5 s (reason 5). It goes back when the direct link receives within 7.5 s again (reason 6). After a congestion switch it waits 0 s, 10 s, 20 s… (at most 60 s) before going back. The reasons are reported in the post-match stats (TURN_CHANGEOVER_REASON/TIME). The TURN server must keep allocations alive for the whole match.

Possible limit: TURN setup checks that one config list has exactly one entry (0x14122eab1). If that list is the peers, TURN mode would only work 1v1 and co-op with a TURN list would fail with "Error CreateMultiplaySession". Test co-op with TURN before relying on it. UNKNOWN

The NAT type value (ntl_nat_type) STATIC

  • 1 = no result yet; 2 or 3 = the NAT test failed. Otherwise a bit set: 0x10 UDP reachable, 0x20+low bits = filtering class (3 = worst/unknown), 0x100–0x2000 UPnP found / mapping / external IP, 0x4000 STUN address ≠ UPnP address, 0x10000 hairpin works, 0x20000 mapping varies (symmetric NAT), 0x100000 port preserved, 0x200000 port parity preserved, high bits = NTL config flags.
  • Our clients' 0x10307533 = UDP reachable, port and parity preserved, UPnP working, STUN ≠ UPnP address (our STUN sees the LAN IP), filtering class 3. The hairpin and mapping tests never ran.
  • The game never branches on it: no strategy change, no refusal, and no "NAT Type" text shown to the player. It's only reported to the server for matchmaking. Our matchmaker can ignore it, or use the symmetric-NAT bit as a hint to prefer TURN.

The NAT test and GateInfo.php

  • 14 tests in phases (MappingTest IA…IV, FilteringTest I/II, hairpin). The extra tests only run if the first reply (IA) carries an OTHER-ADDRESS (0x802C) and a Konami 0xF000 "O573_CR_XADDR" address. Our STUN answers IA only, so the rest are marked skipped, and our logs show only the 32-byte IA probe. Nothing depends on the rest; leave stun.py as it is until the 0xF000 reply layout is proven. STATIC LIVE
  • GateInfo.php: STATUS 200 and API_STATUS 0 (what we send) are fine. API_STATUS 1 + LOG_ACTIVE 1 + PUT_LOG_URL would make clients upload their NTL logs, an optional debug channel.
  • The "SC" game relay (Konami's own full relay) isn't worth building: it needs the undecoded link layer and session logic, with no traffic to learn from. TURN is strictly better.

What the player sees: error texts and server replies

In plain words: every error reply our server can send already has a matching text in the game, often a clear one: "account suspended", "server busy", "your version is out of date", "the room is full". This section shows how the game picks the text, and which replies give players a friendly message instead of a bare error code. All 764 rows of the game's server-error table are resolved to the English text.

How a text is found STATIC

  • Message id = (group number << 16) | entry id, where the group number is the u32 at +4 of each group header in the .str string tables (lookup 0x141497dd0 → 0x1414996f0). Example: 0x0398002f = "Press Any Button". "Failed to connect with opponent." is 0x045b0010, shown by the lobby room screen (0x1410438a0).
  • Server error replies: every command shows an error dialog automatically (on by default, flag at +0x74; about 40 commands switch it off). The text comes from the game's table at 0x1428a1170 (command, ERR code, message id):
    • message id 0xffffffff: no dialog; the screen that sent the command decides (109 rows);
    • message id 0 or 0x01fb00d2: the generic "An unexpected problem has occurred while communicating with the server." plus CODE: = a hash of the command name + "_" + the ERR number, e.g. ZVMY_0079 (163 rows);
    • any other id: that specific text, with no code (492 rows).
  • On-screen codes from the error reporter: TAG_%04d when the site has a sub-code, otherwise TAG + line, optionally followed by an extra value (GNCX_0003_0x20000000). Most codes players see are therefore in the sub-code form (MXNV_0013, CCWR_0014); the error table shows both forms.

How this was found

  • Static reading of the game binary (PES2021.exe 1.01.00), with no debugger and no live server traffic to Konami. A small toolkit (notes/re/functions/tools/) on top of capstone builds a cached cross-reference index of the 37 MB code section in about 10 s. From each command name it finds the request builder, the reply parser and every function that uses the command. STATIC
  • The game's own structure helps a lot. Each command has an …Option class (request; vtable slot 3 = HTTP form builder, slot 1 of the +280 vtable = gate MessagePack packer) and a …Result class whose parser stores every field at a fixed offset. Game code creates commands by name, and the tasks are state machines full of debug strings and source paths (D:\pes2021\PATCH10100\pes21\Source\…\OnlineModeTaskMatchSession.cpp).
  • Cross-checked with our logs: every claim about a request that the game really sent was compared with the decoded traffic of our test sessions. LIVE
  • Reply schemas: notes/re/extract_schemas.py missed keys that the client compares with its std::string == const char* helper (0x140cf3990) instead of memcmp. The fixed extractor finds 1,907 more reply fields in 108 commands (for example the verdict push, division info and all rankings). The catalogue below uses the fixed result. The server's schemas.json has not been regenerated yet, because the server builds default replies from it and that needs a test run.
  • The full per-area reports, with every address, are in notes/re/functions/: net.md, match.md, results.md, rooms.md, coop.md, menus.md, wire.md, survey.md, db.md (with the parser tools/pesdb.py), live.md, nettune.md, messages.md, sweep.md.

What a live test would settle

  • One match through coturn with verbose logging: TURN credentials and certificate check, REQUESTED-TRANSPORT, the relayed-address blob, behaviour when the TURN server is down.
  • Pushing WATCH_GAMEADDPOINT after a Quick Match: whether the rating screen appears, and no OLXH171/186.
  • A Free-lobby room between two clients: whether REQWATCHL requests are sent, the order of SET_GAMEENV and CREATEJOIN_ROOM, and the commands between SETENV and kick-off.
  • A hex dump of the first 64 bytes of every UDP send during matchmaking and kick-off: the lltcp header, hole-punching messages and the match-layer packets.
  • Killing the gate connection mid-menu: what CMD_RECONNECT needs.
